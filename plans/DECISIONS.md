## Standing decisions

- **Frontend is a plain static site — HTML/CSS/vanilla JS, no framework, no build step.** The `stencil-bible-guides` name that seeded this project refers to the *workspace/devcontainer pattern* only; it does not imply Stencil or any frontend framework. (2026-09-06)
  **Why this matters long-term:** the workspace name actively misleads — an early README inferred "Stencil-based web frontend" from it, and any future contributor (or agent) reading the lineage will draw the same wrong conclusion. This project's whole cost/complexity argument rests on a zero-build static site, so re-introducing a framework would quietly break the "tiny, boring, runs cheaply" premise that scopes M4 and the hosting choice in M5.

- **Workspace repo naming: remote is `workspace-`prefixed, local directory is not.** Remote `https://github.com/michaeljthacker/workspace-AreSalmonAtBallardLocks.git`; local folder `DevSpace/workspaces/AreSalmonAtBallardLocks`. The names intentionally differ. (2026-09-06)
  **Why this matters long-term:** the unprefixed GitHub name was already taken by this frontend repo, so the mismatch is deliberate, not drift. Without this recorded, a future contributor is likely to "correct" one side to match the other and break the workspace's `origin` or the `.code-workspace` relative roots, which resolve against the local directory name.

- **`FishCount` stores only atomic per-(date, species) observations — aggregates are always derived, never stored.** A published season/period total is parsed and used as a checksum against the sum of our own per-species rows (a mismatch fails the import run), then discarded. The species vocabulary in `apps/salmon/constants.py` carries no aggregate member and is enforced by a DB-level `CheckConstraint`, so a `TOTAL` row cannot be inserted by a buggy parser or by a hand edit in admin. Non-salmon species observed in the same source table (steelhead) *are* stored as first-class vocabulary members, and unrecognized labels map to an `OTHER` member with the raw label preserved in `source_metadata`; a separate named `SALMON_SPECIES` subset is what every salmon-facing aggregate filters on. (2026-09-07)
  **Why this matters long-term:** the alternative — a reserved `TOTAL` pseudo-species that every read endpoint must remember to exclude — fails silently by inflating a number on a public page, and every new consumer (M3's forecast, M5's charts) is a fresh opportunity to omit the filter. Making the vocabulary closed at the database level converts that class of bug from "possible and invisible" into "impossible." Keeping steelhead stored but outside `SALMON_SPECIES` matters because dropping it at import is lossy and irreversible (recovering it means re-extracting years of history) while the product's answer is specifically about salmon; routing that distinction through one named constant rather than per-query literals is what keeps the two from being conflated. The tradeoff accepted deliberately: adding a species later requires a migration, which is appropriate — a new species at the Locks should force someone to notice.
  **Amended 2026-09-07 (B1-M2-P1 inspection):** the steelhead clause was written on the assumption that steelhead appears in the same source table. It does not — the source publishes only sockeye, Chinook and coho. No `steelhead` vocabulary member was created; the concrete vocabulary is fixed in the entry below. Everything else in this entry (atomic rows only, no aggregate member, DB-enforced vocabulary, the `SALMON_SPECIES` subset, `other` for unrecognized labels) stands as written and is implemented.

- **`FishCount.count` is the daily passage increment for that date and species, in every row — normalized at write time, never cumulative.** If a source publishes cumulative season-to-date figures, the importer converts to daily before writing; the raw published figures and the raw species label are preserved in `source_metadata` alongside `source_url` for audit. A published zero is stored as a row with `count = 0`; a date with no publication gets no row at all — never a placeholder zero. (2026-09-07)
  **Why this matters long-term:** this deliberately inverts the usual store-raw/transform-on-read default, and the reasons are not recoverable from the code. Deltas derived from stored cumulative values are silently wrong across any publication gap, because the missing day's passage folds into the next day's delta with no way to detect it afterward. VISION §21.3 requires distinguishing "no published data" from "a reported count of zero" and forbids interpolation — cumulative storage makes that distinction unrepresentable. Source revisions shift every subsequent cumulative value, which would turn the importer's "insert what's missing" comparison into "update whatever changed." And three independent consumers (the `counts/` endpoint, the forecast, the charts) would each have to reimplement delta logic identically and correctly. Keeping the raw values in `source_metadata` buys the auditability without coupling `count`'s meaning to the source's presentation format. Reversing this after the historical bootstrap loads means migrating every row.

- **A `manually_corrected` latch protects hand-fixed `FishCount` rows; the importer updates freely otherwise.** `FishCount` carries `manually_corrected` (bool, default `False`) and `correction_note` (text), with a `CheckConstraint` requiring a non-empty note whenever the flag is set. The scheduled importer upserts normally but skips any row where the flag is `True`, and reports the count of skipped-because-latched rows in its `ImportRun` message. (2026-09-07)
  **Why this matters long-term:** the obvious-looking alternative, an insert-only importer, is worse and the reason is easy to forget — the official source publishes late, backfills, and revises, so an importer that can never update an existing row can never accept a corrected official figure, leaving a superseded number served permanently with no path to fix it. What is actually needed is not "never update" but "one thing you must not overwrite." Requiring the note at the database level rather than by convention exists because a latched row that silently disagrees with its source and states no reason is precisely the artifact that wastes someone's afternoon months later; surfacing the skipped count in `ImportRun` is what eventually gets a stale correction un-latched.

- **`FishCount` uniqueness is `(date, species)`, not `(date, species, source)`.** `source` records which retrieval route produced a row; it is provenance, never identity. Decided by inspection on 2026-09-07: salmon entering the Lake Washington ship canal are counted at one physical location (the Ballard Locks fish ladder) by one co-management arrangement (WDFW with the Muckleshoot Indian Tribe), and no independent second count of the same fish exists. The two retrieval routes found — the WDFW HTML counts page and the `pssp-count.wdfw-fish.us` chart JSON behind it — are two publications of that single series, and they overlap: both carry sockeye for the current season. Evidence and per-source detail in `docs/data-sources.md`. (2026-09-07)
  **Why this matters long-term:** including `source` in the key looks like harmless provenance-keeping and is actually the double-counting bug in disguise — the two routes overlap on sockeye, so a `(date, species, source)` key would happily store the same real-world observation twice and every `SUM(count)` behind the public answer, the forecast, and the charts would silently inflate. Choosing the narrower key forces the importer to *reconcile* two publications of one series rather than accumulate both, which is the behavior actually wanted. The cost is accepted knowingly: if a genuinely independent second count ever appears (a different agency counting the same ladder), it cannot be stored side by side without a migration — and that is the right place to stop and think, because at that point someone has to decide which series the public answer uses, and a schema that quietly stored both would let that decision go unmade.

- **The species vocabulary is `sockeye`, `chinook`, `coho`, `other` — and steelhead is deliberately absent.** Fixed from the real source data on 2026-09-07: the WDFW publication reports exactly three species at this ladder, which are exactly the three VISION §21.1 names, and the chart JSON reports sockeye alone. `other` is the catch-all for an unrecognized source label, with the raw label preserved in `source_metadata`; it is a vocabulary member but is excluded from `SALMON_SPECIES`, so an unknown label can never inflate the salmon number. The vocabulary is enforced by a DB-level `CheckConstraint`, so adding a species is a migration. (2026-09-07)
  **Why this matters long-term:** the earlier Q-003 ruling assumed steelhead shared the source table and made it a first-class member; inspection showed it is not published here at all, and a vocabulary member for data that does not exist is speculation frozen into a database constraint. What survives, and is the durable part, is the *shape*: `SALMON_SPECIES` is a named subset deliberately kept distinct from the full vocabulary even though the two currently differ only by `other`. That redundancy is the point — the day the co-managers add a non-salmon species (steelhead is the obvious candidate), it becomes a vocabulary member without becoming a salmon, and no aggregate query has to be found and revisited. Collapsing the two into one list because they look alike today is precisely how a steelhead ends up inside an answer about salmon.
